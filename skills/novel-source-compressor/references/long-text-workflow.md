# Long-Text Workflow

## 1. 文件盘点

先列出文件和大小，识别目录、分卷、章节标题、编码、重复版本和可能的正文/笔记混杂。按用户指定版本优先；没有指定时不要把不同版本静默拼接，先给出版本选择。

## 2. 切分原则

优先在卷、章、场景、明显视角切换处切分。固定字符数只用于单个章节过大时的二次切分，并为每个子块保存 `parent_chapter` 和顺序。每块都要带文件/章节定位，避免合并后失去回查能力。

## 3. 三层摘要

### 局部层

每个块只记录新状态：行动、选择、信息、关系、代价、资源和承诺。重复气氛或相同心理不重复计入，除非重复本身构成执念或伏笔。

### 弧层

按连续目标合并块，检查目标是否改变、阻力是否升级、低谷是否有代价、出口是否产生新压力。一个弧只有事件没有选择时，标记为“待诊断”，不要擅自补人物动机。

### 全局层

将弧组织为卷/幕/阶段，生成时间线、人物弧和伏笔表。全局摘要必须能回答“故事从哪里变成了什么”，而不是把局部摘要简单串起来。

## 4. 断稿、完整稿和多视角稿

- **完整稿**：仍检查结尾是否回收核心承诺；完成不等于最后一章存在。
- **未完成稿**：标记最后稳定点，区分已发生和作者尚未写出的部分；不要替用户把未写章节伪装成原文摘要。
- **多视角稿**：按时间线合并同一事件的不同视角，保留知识差和互相矛盾的叙述，不强行选一个“客观真相”。
- **多文件/多版本**：先建立版本矩阵，使用 `source_status: conflicting`，让用户选择主版本或输出并行大纲。

## 5. 增量合并

若已有 `source_outline_state`，先读取旧账本与新章节的前后窗口；只更新受影响节点。任何新结论都要标注 `added`、`revised`、`conflicting` 或 `deprecated`，保留 `change_log`。不能因为新章节更近末尾，就抹去早期仍未回收的承诺。

## 6. 压缩深度

- `quick`：故事核心、主要人物、卷级结构、末尾状态。
- `standard`：以上内容 + 章节索引、关系/连续性摘要、伏笔表；默认档。
- `deep`：以上内容 + 章节/场景卡、证据锚点、知识差、资源与风险，适合直接交给续写规划。

用户要求“从原文续写”时使用 `standard` 全局层加 `deep` 尾部窗口，避免为了压缩速度丢掉续写起点。
